# world-cache-keepalive（缓存保温）

上下文静下来太久，上游的前缀缓存会过期；再被叫醒的那一轮要按整份前缀重新计价。
这个 World 在空档变长之前补一条「不要求回应」的内部事件，把缓存续上。

它不说话、不调用工具、不往提示词里加一个字、不写盘。

> ## 先读这一段：下文所有数字都来自 **LongCat-2.5**
>
> `75 分钟`、`26–38 万 token`、`三千多拍`、`81%`、默认的 `40`——这些**不是这个插件的性质，是一台模型的性质**。
> 换一个上游，缓存的有效期、计价方式、甚至「做不做前缀缓存」都可能完全不同：
>
> - 有的厂商前缀缓存只有几分钟；
> - 有的按整点、按小时失效；
> - 有的缓存根本不便宜（那就没有省的余地，反而多花）；
> - 有的不在 usage 里回报缓存命中（`cacheHitTokens` 恒为 0），那这个插件无从判断、也不该开。
>
> **所以装之前请先量一遍你自己的：见「换模型之前先量一遍」。** 照抄 40 分钟只在你用的也是 LongCat 时才成立。

## 为什么要有它

按缓存计价之后，一次模型调用的账单只取决于**缓存命中多少**：

- 缓存热着：只付这一轮新增的那几百 token；
- 缓存过期：整份前缀按未命中重算。

以下是 **LongCat-2.5 + Coopanion**、连续四天 `usage.jsonl` 的实测：

| 事实（LongCat-2.5 实测） | 数据 |
|---|---|
| 缓存有效期 | **约 75 分钟**——73 分钟还命中 99.8%，78 分钟直接 0% |
| 单次冷启动的未命中 | 26–38 万 token（上下文越长越贵） |
| 一次心跳的未命中 | 约 100 个新 token（缓存命中的部分不计费） |
| 换算 | 一次冷启动 ≈ **3500 拍心跳** |
| 冷启动在全部未命中里的占比 | 四天 20 次，占 **81%** |

金额按 **LongCat 资源包口径**折算：`29.9 元 / 5000 万 token`，约 **0.6 元/百万**，且**缓存命中不计 token**。
按这套口径，这台机器三天实测是 **每天 ¥0.4–2.0**，一个包大约撑一个月。

也就是说：在这套计价下，一天里花钱的几乎全是「隔了两三个小时第一次开口」这件事，
而不是她说得多——热调用只计那几百个新 token。而夜里那些空档不是没人叫她，
是事件被标成不唤醒、攒着不投递，直到某个真正会唤醒的事件到来，才整批放出、一次性付掉整份前缀。

**所以只要在空档变长之前敲一下，就能把这 81% 砍掉大半。**

成本这边：一天 36 拍大约 **¥0.002**（半分钱都不到），而消掉一次冷启动省 **¥0.21**。
换句话说，**敲一天的心跳，只要省下一次冷启动就回本 90 多天**。

> 如果你用的不是「缓存不计 token」的资源包，而是按牌价逐 token 计费（LongCat 牌价：输入 2 元/百万、
> 缓存输入 0.04 元/百万、输出 8 元/百万），这套账要重算：心跳每拍也要付「整份前缀再发一遍」的钱，
> 一次冷启动约合 65 拍，收益还在但薄得多。

（上面所有数字的适用范围同样只有 LongCat-2.5。别的模型上，先量，再判断这套账成不成立。）

## 换模型之前先量一遍

包里带了一个脚本，它只读 `usage.jsonl`，不联网、不改任何东西：

```powershell
# 默认去 Coopanion 的安装目录找 usage.jsonl
node scripts/measure.ts

# 或者指定文件
node scripts/measure.ts C:\path\to\usage.jsonl
```

它按「距上次调用的间隔」分桶，算出每一桶的未命中率，然后给出两个数：

- **缓存有效期落在哪两个数之间**：最长的「命中良好」空档，和最短的「超过它就整段未命中」空档；
- **`afterMinutes` 该填多少**：取有效期的六成左右，再取整到 5 的倍数（插件允许 10–70）。

判据只有两条，很容易自己复核：

```
命中良好：gap ≥ 3 分钟，且未命中 < prompt 的 10%
整段未命中：gap ≥ 3 分钟，且未命中 > prompt 的 50%
```

（小于 3 分钟的样本会被跳过：交接、改配置这些动作会在那个量级上制造「整段未命中」，
那不是缓存过期，混进去会把有效期算小。）

三种结果对应三种处理：

| 脚本说什么 | 说明 | 怎么办 |
|---|---|---|
| `cacheHitTokens` 全是 0 | 上游不回报缓存命中，或不做前缀缓存 | **别开**，一分钱省不到 |
| 一次「命中良好」都没有 | 每次调用都整段未命中 | **别开**，说明上下文每轮都在重建 |
| 给出一段区间 | 正常，量到了 | 把建议值填进 `afterMinutes`，跑几天再复量一次 |

## 它做什么

```
每 tickSeconds 秒 → statSync(<data>/usage.jsonl).mtimeMs
                  → 五道闸
                  → 都过了才 pushDeferred({type:'cache-keepalive.beat', origin:'internal'}, {trigger:'flush'})
```

用 `usage.jsonl` 的修改时间是刻意的：宿主每轮模型调用都会往这份账里追加一行，
所以它的 mtime 就是「上一次调用」的准确时刻。**不用自己记账**，重启也不丢；
而且心跳自己那一轮也会写账，于是下一拍自动被推后——它是自限速的。

五道闸，每一条都留一句话给人看（设置页的灯会显示它），
不然「没推」到底卡在哪一步只能猜：

| 顺序 | 条件 | 不推时记的话 |
|---|---|---|
| 1 | 开关关着 | `开关关着` |
| 2 | 上一拍距今 < 阈值 | `上一拍刚推过（N 分钟前）` |
| 3 | 距上次调用 < 阈值 | `距上次调用 N 分钟，还没到 40` |
| 4 | 落在夜间窗口里 | `夜里 2–7 点不补拍` |
| 5 | 今天已到上限 | `今天已经补了 N 拍（上限 48）` |

## 为什么不做成提示词

「记得每半小时敲一下自己」这种话，模型不会真的照做——这是这个项目里反复验过的结论：
**提示词管不住动作，回执和事件能。** 所以保温必须是一个外部定时器，
而不是写进人格的一段嘱咐。

同理，它也不该给模型任何工具或环境提示：她一旦知道「有个心跳」，就会去查它。

## 配置

| 键 | 默认 | 范围 | 说明 |
|---|---|---|---|
| `enabled` | `false` | 开/关 | 装上之后先保持关着，量完再开 |
| `afterMinutes` | `40` | 1–1440 | 空档阈值。**40 是 LongCat-2.5 的值**，换模型先用脚本量。填得比真实有效期长，插件就等于没开 |
| `tickSeconds` | `15` | 5–300 | 多久看一次表。改完下一拍生效，不用重启 |
| `text` | `''` | 字符串 | 正文模板，`{time}` 换成当前时刻；留空用默认那句 |
| `quietHours` | `''` | `2-7` / `23-7` | 夜里不补拍的时段。**留空＝全天**：空档最长的就是夜间，留空才省得最多 |
| `maxPerDay` | `48` | 0–240 | 0 表示不限。防手滑把模型一直叫醒 |

阈值与看表间隔都是**每拍现读**的，设置页改完下一拍生效，不需要重启。

### 关于正文，一句提醒

默认正文只有一句：

```
（静默心跳：现在是 14:00）
```

它很省，但**它没告诉模型「这不是对方说的」**。模型有可能把它当成一句搭话回过来
（桌宠里就冒泡了），也可能读成「到点了，该做点什么」，转手去查生态箱、写记忆——
那一拍就变成五轮。

稳一点的写法（多这二十来个字，按资源包口径一天 36 拍只多 **¥0.0004**，可以忽略）：

```
（静默心跳：现在是 {time}。不是ta说的，不用回、不要调用工具。）
```

## 安装

**从应用市场装**：搜「缓存保温」（包名 `world-cache-keepalive`），装上即可。

**或从 npm 装**：

```powershell
# 在 Coopanion 的扩展目录下（data/extensions）
pnpm add world-cache-keepalive
```

装完重启一次（新 World 要重新装配），然后到设置页把「缓存保温」打开，并做两件事：

1. 先把 `afterMinutes` 换成 **`scripts/measure.ts` 给你的那个值**——默认 40 只对 LongCat-2.5 成立；
2. 想让她别半夜醒就填 `quietHours`（例如 `2-7`），留空表示全天补拍。

其余三个键（`tickSeconds` / `text` / `maxPerDay`）默认值就能用，可以先不动。

## 验证

```powershell
# 启动日志里应该有
World 已启动: cache-keepalive
```

设置页「缓存保温」有一盏灯，悬停显示当前状态：

```
已补一拍（今天 3 拍）｜阈值 40 分钟｜距上次调用 41 分钟
```

隔两小时回头看 `usage.jsonl`：应该不再出现「整段未命中」的记录，
而是每 40 分钟多一条 `output ≈ 20~40` 的小记录。

这个判断也只在 LongCat 上成立——别的模型上，用 `scripts/measure.ts` 复量，
看「整段未命中」的条数有没有真的降下来。

## 已知边界

它只能治「闲着太久的冷启动」。下面两类它管不了，别误会：

- **重启后的第一次调用**：前缀内容变了（跨天、记忆文件变了），跟间隔无关；
- **上下文交接后的第一次调用**：前缀刚重建，同样是一次全价。`onHandoffEnded()` 只是让它别急着补，不是免单。

按四天的真实数据（LongCat-2.5），这两类占全部未命中的 27%，剩下那 53% 才是这个插件的地盘。
